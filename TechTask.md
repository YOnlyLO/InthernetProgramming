# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## на разработку веб-сервиса «FRIENDWISH»

---

## 1. Общие сведения

**Наименование проекта:** FRIENDWISH.

**Тип системы:** веб-приложение с клиент-серверной архитектурой.

**Назначение системы:** создание удобного сервиса для формирования и просмотра списков желаний пользователей, позволяющего друзьям и близким узнавать, какие подарки пользователь хотел бы получить.

Система должна предоставлять зарегистрированным пользователям возможность создавать собственный список желаний, добавлять в друзья других пользователей и просматривать их списки желаний.

**Основная задача проекта** — упростить процесс выбора подарков для близких людей за счет централизованного хранения информации о желаемых товарах.

---

## 2. Цели и задачи проекта

### 2.1. Цель проекта

Разработать веб-сервис, позволяющий пользователям:

- создавать и редактировать собственный список желаний;
- добавлять товары и другие желаемые объекты в список;
- указывать название, описание, цену и ссылку на товар;
- находить других пользователей;
- добавлять пользователей в список друзей;
- просматривать списки желаний друзей;
- получать актуальную информацию о желаемых подарках;
- управлять собственной учетной записью.

### 2.2. Основные задачи

В рамках разработки необходимо реализовать:

- регистрацию и авторизацию пользователей;
- управление профилем пользователя;
- формирование списка желаний;
- добавление, редактирование и удаление желаний;
- систему поиска пользователей;
- систему друзей;
- просмотр списков желаний друзей;
- административное управление пользователями;
- разграничение прав доступа;
- взаимодействие клиентской и серверной частей через REST API;
- хранение данных в реляционной базе данных PostgreSQL.

---

## 3. Пользователи системы

В системе предусматриваются следующие категории пользователей.

### 3.1. Зарегистрированный пользователь

Зарегистрированный пользователь должен иметь возможность:

- авторизоваться в системе;
- управлять собственным профилем;
- создавать список желаний;
- добавлять товары в список;
- редактировать и удалять свои желания;
- искать других пользователей;
- отправлять и принимать заявки в друзья;
- просматривать списки желаний друзей;
- выходить из учетной записи.

### 3.2. Администратор

Администратор должен иметь расширенные права и возможность:

- просматривать зарегистрированных пользователей;
- просматривать информацию об учетных записях;
- изменять роли пользователей;
- блокировать и разблокировать пользователей;
- выполнять административное управление данными системы.

Административные функции должны быть доступны только пользователям с соответствующей ролью.

---

## 4. Функциональные требования

### 4.1. Регистрация пользователя

Система должна предоставлять форму регистрации.

При регистрации пользователь должен указать:

- имя пользователя;
- юзернейм;
- адрес электронной почты;
- пароль;
- подтверждение пароля.

Система должна выполнять проверку введенных данных.

Необходимо предусмотреть:

- проверку обязательных полей;
- проверку корректности электронной почты;
- проверку совпадения пароля и его подтверждения;
- проверку уникальности учетной записи;
- безопасное хранение пароля в виде хэша.

После успешной регистрации пользователь получает возможность авторизоваться в системе.

---

## 5. Авторизация

Система должна предоставлять возможность входа в учетную запись по учетным данным пользователя.

После успешной авторизации сервер должен предоставить клиентскому приложению JWT-токен.

JWT используется для подтверждения личности пользователя при последующих запросах к защищенным ресурсам.

Неавторизованный пользователь не должен иметь доступа к функциям, предназначенным для зарегистрированных пользователей.

На стороне Frontend необходимо реализовать защиту маршрутов с помощью Angular Guards.

---

## 6. Профиль пользователя

Каждый зарегистрированный пользователь должен иметь профиль.

В профиле должна отображаться следующая информация:

- имя пользователя;
- юзернейм;
- адрес электронной почты;
- аватар;
- список друзей;
- основная информация об учетной записи.

Пользователь должен иметь возможность:

- изменить имя пользователя;
- изменить аватар;
- изменить другие доступные персональные данные;
- изменить пароль;
- просматривать список своих друзей.

Изменение данных должно выполняться с использованием REST API.

---

## 7. Система друзей

Одной из основных функций сервиса является возможность формирования списка друзей.

Пользователь должен иметь возможность найти другого зарегистрированного пользователя и отправить ему заявку в друзья.

Необходимо реализовать следующие состояния:

- заявка отправлена;
- заявка принята;
- заявка отклонена;
- пользователь является другом;
- пользователь не является другом.

Пользователь должен иметь возможность:

- отправлять заявки в друзья;
- принимать заявки;
- отклонять заявки;
- удалять пользователей из списка друзей;
- просматривать список друзей.

Доступ к списку желаний другого пользователя должен предоставляться только при наличии соответствующего отношения «друзья».

---

## 8. Список желаний

Основным функциональным элементом системы является список желаний пользователя.

Каждый пользователь должен иметь возможность создавать собственный список желаний.

Каждая запись списка должна содержать:

- уникальный идентификатор;
- наименование товара;
- краткое описание;
- ссылку на товар;
- цену;
- идентификатор пользователя — владельца желания.

**Пример записи:**

| Поле         | Значение                                         |
| ------------ | ------------------------------------------------ |
| Наименование | Sony WH-1000XM6                                  |
| Описание     | Беспроводные наушники с активным шумоподавлением |
| Ссылка       | Ссылка на страницу товара                        |
| Цена         | 39 990 ₽                                         |

---

## 9. Управление желаниями

Авторизованный пользователь должен иметь возможность:

### Добавление

Пользователь заполняет форму с информацией о желаемом товаре:

- название;
- описание;
- ссылка;
- цена.

После отправки формы данные проходят клиентскую и серверную валидацию и сохраняются в базе данных.

### Редактирование

Пользователь должен иметь возможность изменить информацию о любом желании, принадлежащем ему.

### Удаление

Пользователь должен иметь возможность удалить желание из своего списка.

Перед удалением желательно предусмотреть подтверждение действия.

### Просмотр

Пользователь должен иметь возможность просматривать собственный список желаний.

Также пользователь должен иметь возможность просматривать списки желаний своих друзей.

---

## 10. Просмотр списка желаний друга

При открытии профиля друга пользователь должен иметь возможность перейти к его списку желаний.

Для каждого желания должна отображаться:

- фотография или визуальное представление товара при наличии;
- название;
- краткое описание;
- цена;
- ссылка на товар.

Пользователь не должен иметь возможности изменять или удалять желания другого пользователя.

Таким образом, права владельца списка и стороннего пользователя должны быть разделены.

---

## 11. Поиск пользователей

Система должна предоставлять возможность поиска зарегистрированных пользователей.

Поиск должен осуществляться, например, по:

- имени пользователя;
- юзернейму.

Результаты поиска должны содержать основную публичную информацию о найденном пользователе и позволять отправить заявку в друзья.

---

## 12. Административная панель

Для пользователей с ролью администратора должна быть предусмотрена отдельная административная панель.

Администратор должен иметь возможность просматривать список пользователей.

Для каждого пользователя может отображаться:

- идентификатор;
- имя пользователя;
- электронная почта;
- роль;
- статус учетной записи.

Администратор должен иметь возможность:

- изменять роль пользователя;
- блокировать пользователя;
- разблокировать пользователя.

Административные API-методы должны быть защищены проверкой роли пользователя.

На стороне ASP.NET Core необходимо использовать механизм авторизации по ролям, например:

```csharp
[Authorize(Roles = "Admin")]
```

---

## 13. Безопасность

Система должна обеспечивать базовый уровень безопасности пользовательских данных.

Необходимо реализовать:

- хранение паролей только в виде хэшей;
- JWT-аутентификацию;
- авторизацию защищенных API-методов;
- разграничение прав пользователей;
- серверную валидацию входных данных;
- защиту административных функций;
- предотвращение SQL-инъекций посредством использования EF Core;
- безопасную обработку пользовательского ввода.

Пользователь не должен иметь возможности получить или изменить данные другого пользователя путем ручного изменения идентификаторов запросов.

### Спринт 2. Backend

**Ответственный:** Степанов Данил (YOnlyLO). Подготовительная задача по frontend — Сыромятников Андрей (AndreySyromyatnikov).

**Цель спринта:** реализовать серверную часть приложения — REST API на ASP.NET Core с хранением данных в PostgreSQL. По итогам спринта все функции системы доступны через API и проверяются через Swagger.

**Как работает backend.** Клиент (Angular) отправляет HTTP-запросы к REST API. Контроллеры принимают запрос, проверяют входные данные и права доступа и вызывают сервисы с бизнес-логикой. Сервисы работают с базой данных через EF Core. При входе пользователь получает JWT-токен и передает его в заголовке `Authorization: Bearer <token>` при каждом запросе к защищенным методам. Идентификатор текущего пользователя берется из токена, а не из параметров запроса, поэтому получить или изменить чужие данные подменой id нельзя.

**Задачи:**

1. **Модель данных и база данных.** Сущности `User`, `Wish`, `Friendship` (со статусом заявки: отправлена, принята, отклонена), роли пользователей (`User`, `Admin`) и статус учетной записи (активна, заблокирована). Настройка `DbContext`, подключение к PostgreSQL, миграции EF Core.
2. **Регистрация и авторизация.** Регистрация с серверной валидацией (обязательные поля, формат email, совпадение паролей, уникальность email и юзернейма), хэширование паролей, вход с выдачей JWT, настройка JWT-аутентификации. Заблокированный пользователь не может войти.
3. **Профиль пользователя.** Получение и изменение своего профиля (имя, аватар, другие данные), смена пароля с проверкой текущего.
4. **Список желаний.** CRUD для желаний текущего пользователя. Изменять и удалять желание может только его владелец. Список желаний другого пользователя отдается только при наличии дружбы.
5. **Друзья и поиск.** Поиск пользователей по имени и юзернейму. Отправка, принятие и отклонение заявок, удаление из друзей, список друзей, входящие и исходящие заявки.
6. **Административное API.** Список пользователей, изменение роли, блокировка и разблокировка. Методы защищены `[Authorize(Roles = "Admin")]`.
7. **Документация API.** Подключение Swagger с поддержкой JWT, единый формат ошибок, описание запуска backend в README.
8. **Подготовка frontend к интеграции** (AndreySyromyatnikov). Макеты основных страниц (вход, регистрация, профиль, список желаний, друзья, админ-панель), TypeScript-модели данных и Angular-сервисы для работы с API по таблице методов ниже.

**Основные методы API:**

| Метод  | Адрес                                | Назначение                     |
| ------ | ------------------------------------ | ------------------------------ |
| POST   | `/api/auth/register`                 | Регистрация                    |
| POST   | `/api/auth/login`                    | Вход, получение JWT            |
| GET    | `/api/profile`                       | Свой профиль                   |
| PUT    | `/api/profile`                       | Изменение профиля              |

| DELETE | `/api/wishes/{id}`                   | Удаление желания               |

### Спринт 3. Frontend

**Ответственный:** Сыромятников Андрей (AndreySyromyatnikov). Поддержка backend — Степанов Данил (YOnlyLO).

**Цель спринта:** реализовать клиентскую часть на Angular и подключить ее к REST API из второго спринта.

**Задачи:**

1. **Каркас приложения.** Структура модулей и компонентов, маршрутизация, общий макет (шапка, навигация), сервисы для работы с API, HTTP-interceptor для добавления JWT в запросы и обработки ошибок 401/403.
2. **Регистрация и вход.** Формы с клиентской валидацией, хранение токена, выход из учетной записи. Защита маршрутов через Angular Guards: `AuthGuard` для авторизованных пользователей и `AdminGuard` для администраторов.
3. **Профиль.** Просмотр и редактирование профиля, смена аватара и пароля, список друзей.
4. **Мой список желаний.** Просмотр, добавление, редактирование и удаление желаний, подтверждение перед удалением, валидация формы.
5. **Друзья и поиск.** Поиск пользователей, отправка заявки, входящие и исходящие заявки, принятие, отклонение и удаление из друзей.
6. **Список желаний друга.** Страница профиля друга и его списка желаний в режиме только для просмотра, без кнопок изменения.

8. **Интерфейс.** Единый стиль, адаптивная верстка, индикаторы загрузки и сообщения об ошибках.
9. **Интеграция backend с клиентом** (YOnlyLO). Настройка CORS для Angular-приложения, загрузка и отдача аватаров, исправление и доработка API по замечаниям, найденным при подключении frontend.

**Результат спринта:** работающее веб-приложение, связанное с backend; описание запуска frontend в README.
